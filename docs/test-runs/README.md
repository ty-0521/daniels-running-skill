# 真实对话测试留下的产物

这个目录里**没有范例，全是证据**。

2026-11 做了两轮连续对话测试：把本 skill 装进一个 agent，用同一个人的口吻从头问到尾，
**每个回合的问题都由上一回合的答案决定**。测的不是"它能不能算对"，是
**"它会不会在没数的时候编数"**。

## 第一轮：十回合（改代码之前的版本）

结论：数值层很稳，流程层不稳。下面三份表都是那一轮留下的。

| 文件 | 它当时的问题 |
|---|---|
| `半马12周计划.md` | 更早的一版，把「12 周排不出合规表」这个结论用偷换定义的方式糊过去了 |
| `半马18周计划.md` | 写着「`check_progression` → 0 违规」，实际跑出来有 1 处：第 13 周加量距上次只有 2 周。前 10 周的长跑占比 33.3%/31.2%，超 30% 上限，文件里没提 |
| `半马32周计划.md` | 比赛日 `2027-06-27` 是它自己按「今天 + 32 周、取最近周日」倒推的，用户从没说过这个日期 |
| `plan.json` | 上面那张 18 周表的机器可读版本，用来回测 |

起点 `18 km/周` 在这几份里都当成事实写，实际是它按一个自己估的配速折出来的。
用户从头到尾没报过周跑量。

**所以这几份只能当反例读。** 日期、跑量来源、合规声明都不可信。

## 第二轮：六回合（加了 intake / audit / dates 之后）

| 文件 | 结果 |
|---|---|
| `half-marathon-2027-04-18.md` | 20 周半马计划。**`audit_plan(...).passed = True` 是真的**——我独立重建了那张表跑了一遍，并且它也主动报告了「若按 4 周间隔会挂在第 7/10/13/16 周」，我复现的四周边界一模一样 |
| `plan_builder.py` | 生成上表的脚本。注意它**不是生成器，是回放器**（见下面「它自己犯的两个错」） |

这一轮的四处小毛病都不是老毛病：摘要写「长跑始终 = 30%」实际只有前三周顶到 30%、
「每次 +1.6 × 4 次」（+6.4）与实际步长（+6.1~6.2）不符、聊天里把 23 周起点写成 11-08（应为 11-09）、
把 6:24/km 说成「阈值附近」（在它自己估的 VDOT 31~34 区间里其实是马拉松配速到 E 快端之间）。

### 它自己犯的两个错，值得照着改

`plan_builder.py` 里原本有这两行，是「手算代替调函数」的活标本：

```python
sys.path.insert(0, r"C:\Users\ty\.dsh\skills\daniels-running-skill")  # 只在这台机器能跑
START = datetime.date(2026, 11, 30)                                   # 写死的起点
```

**两行现在都改了**（因为把脚本发到别的机器上根本跑不起来）：

* 路径改成 `Path(__file__).resolve().parents[2]`，跟着文件位置走；
* 起点改成 `d.plan_window(20, RACE)[0]`，跟着比赛日走。

改完输出与原来一模一样（起点仍然是 2026-11-30），但**现在它是算出来的，不是抄下来的**——
下次换一个比赛日，表会自己跟着动，不会静默错位。

库里明明有 `d.plan_window`，起点就不该手写。这个说法没变，只是代码现在对上了。

## 第三轮：豆包 agent 端到端（2026-11-13）

不是人测的，是一个能跑 Python 的 agent（豆包工作模式，读 `D:\training` 这份工作副本）
从零排出来的一张 18 周半马表。留着当**外部跑通的证据**。

| 文件 | 说明 |
|---|---|
| `build_hm18_persona.py` | 生成与自审脚本。人物数据虚构；每个配速、上限、周数都走 `daniels` 函数 |
| `plan_hm18_persona.json` | 上表的机器可读版本，可直接 `python daniels_cli.py audit 它` |
| `半马18周计划_虚拟人物.md` | 给人读的版本，开头写明「虚构」「合规结论只来自 audit_plan」 |

独立复核：

```
$ python daniels_cli.py audit docs/test-runs/plan_hm18_persona.json
通过：18 周，6 类检查全过（cap、incomplete、race_volume、sum、progression、base）
```

**这一份和前两轮不同：它是通过的。** 前两轮留着是因为它们错了，这一轮留着是因为它对——
而且证明这套东西换个 agent、换台机器，行为一致。

## 为什么留着

因为改完之后，这些表都能被机器审出来，可以当回归基线用：

```bash
python -m daniels audit docs/test-runs/plan.json      # 必须退出码 2（不通过）
```

`tests/test_docs.py` 里有一组 `TestArchivedCounterexample`，断言的反例**永远**判不通过。
一旦某次改动让它"通过"了，说明检查被改松了——那比任何一个功能 bug 都严重，
因为它意味着以后所有表都会"通过"。

## 测试方法本身

如果要在别的项目上复用这套方法，要点只有一条：

**每个回合的问题，必须由上一回合的答案决定。**

不要一口气抛十个不相关的问题——那样测出来的是"模型各自应付孤立问题的能力"，
而真实使用中，人是一句接一句追问的。中间任何一步它编了数，后面全建在那个数上，
只有在连续追问里才看得出来。
